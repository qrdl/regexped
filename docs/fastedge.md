# Using Regexped in Gcore FastEdge

FastEdge runs Rust-based WASM applications using the `proxy-wasm` ABI, and HTTP applications built as `wasi:http` components, in Rust, Go or JavaScript. For the first, regexped is embedded as a separate WASM module that is merged into the final binary — the same workflow as any Rust host — and most of this page covers that route. The last three sections cover component applications: one in Rust, one in Go built with componentize-go, and one in JavaScript built with the FastEdge JS SDK.

## Configuration

```yaml
# regexped.yaml
output:        "final.wasm"    # merged output (triggers embedded mode)
wasm_file:     "regexps.wasm"  # compiled regexp WASM (intermediate)
import_module: "regexps"       # Rust module name in generated stubs
stub_file:     "stubs.rs"      # generated Rust FFI stubs

patterns:
  - name: hostname             # used by both patterns below
    regexp: '[a-zA-Z0-9.\-]+\.[a-zA-Z]{2,}'

  - regexp:    '^([a-zA-Z0-9._%+-]+@(?&hostname))$'
    match_func: "match_email"

  - regexp:    '^https?://(?&hostname)(/[^\s]*)?$'
    match_func: "url_match"

  - regexp:    '(?i)(?:<\s*(?:script|iframe|...)\b[^>]*>|\bon\w+=|javascript\s*:)'
    find_func:  "find_xss"
```

`(?&hostname)` inserts the regexp of the pattern named `hostname`, so both
patterns share one host-name definition ([references.md](references.md)).

The `output` field puts regexped into embedded mode: the regexp WASM imports memory from a `"main"` host module instead of owning it. `regexped merge` combines both into `final.wasm`.

## Build

```bash
# 1. Generate Rust stubs
regexped generate --config=regexped.yaml        # → stubs.rs

# 2. Build Rust app to WASM
cargo build --target wasm32-wasip1 --release    # → target/.../validate.wasm

# 3. Compile regexp patterns to WASM
regexped compile --config=regexped.yaml         # → regexps.wasm

# 4. Merge into final binary
regexped merge --config=regexped.yaml \
  --main=target/wasm32-wasip1/release/validate.wasm \
  regexps.wasm                                  # → final.wasm
```

See [`examples/fastedge/validate/Makefile`](../examples/fastedge/validate/Makefile) for a complete Makefile.

## Usage in Rust

Include the generated stubs and call the regexp functions through the module namespace:

Every call has THREE outcomes, not two. Besides "matched" and "did not match"
there is **`Err`** — a pattern compiled to the Backtracking engine ran out of
memory for its search, so the engine cannot say whether the input matches. Collapsing it
into "did not match" is an input-length-dependent false negative, which for a
validator means failing OPEN. Match all three arms.

```rust
include!("stubs.rs");   // generated by regexped generate

// match_func → Result<Option<usize>>: the end position, None, or Err when the
// engine could not answer.
match regexps::match_email(p.email.as_bytes()) {
    Ok(Some(_)) => {}                       // valid
    Ok(None)    => return reject("invalid email address"),
    Err(err)    => return cannot_validate(err),   // 500, not 400
}

match regexps::url_match(p.url.as_bytes()) {
    Ok(Some(_)) => {}                       // valid
    Ok(None)    => return reject("invalid URL"),
    Err(err)    => return cannot_validate(err),
}

// find_func → an iterator over the matches at or after `offset`, yielding
// Result<(start, end)>. The offset is a real parameter: pass 0 to scan from
// the beginning.
match regexps::find_xss(p.descr.as_bytes(), 0).next() {
    Some(Ok(_))   => return reject("description contains potential XSS"),
    None          => {}                     // clean
    Some(Err(err)) => return cannot_validate(err),
}
```

`cannot_validate` is a 500 rather than a 400 on purpose: the request was not
shown to be invalid, the engine simply could not decide.

See [rust-api.md](rust-api.md) for the full Rust API reference.

See [`examples/fastedge/validate/`](../examples/fastedge/validate/) for the complete example above (individual `match_func`/`find_func` patterns).

## Set composition example: multi-pattern URL filtering

[`examples/fastedge/url-guard/`](../examples/fastedge/url-guard/) demonstrates the `sets:` composition feature instead — scanning a URL against 22 attack-signature patterns (SQL injection, path traversal, XSS, etc.) in one pass via `scan_any`:

```yaml
sets:
  - name: "attacks"
    scan_any: "scan_url"    # non-anchored: ONE matching pattern id, no position
    emit_name_map: true      # so attacks_pattern_name(id) can name the attack type
    patterns: all
```

```rust
// scan_any answers "does anything match, and which" in ONE pass over a union
// automaton — no position, no extent, which is all a block decision needs.
// The third arm is not optional: Err means the engine could not ANSWER, so
// treating it as clean would fail OPEN on an input crafted to exhaust the
// Backtracking engine's memory.
match patterns::scan_url(&url, 0) {
    Ok(Some(pattern_id)) => {
        let attack = patterns::attacks_pattern_name(pattern_id);
        self.send_http_response(
            403,
            vec![("Content-Type", "text/plain")],
            Some(format!("Forbidden: {} detected", attack).as_bytes()),
        );
        return Action::Pause;
    }
    Ok(None) => {}      // nothing matched — fall through to Action::Continue
    Err(err) => {
        // Fail CLOSED: the request was not shown to be clean, so it is not
        // forwarded. Every arm that is not `Ok(None)` must TERMINATE the
        // request — an empty arm here reads as "fail closed" and behaves
        // exactly like `Ok(None)`.
        println!("Cannot scan URL: {err}");
        self.send_http_response(
            500,
            vec![("Content-Type", "text/plain")],
            Some("Cannot scan request".as_bytes()),
        );
        return Action::Pause;
    }
}
```

See [sets.md](sets.md) for the full `sets:` schema and output format.

## Component Model example: an HTTP app in Unicode mode

[`examples/fastedge/script-detect/`](../examples/fastedge/script-detect/) is a
FastEdge HTTP application built the other way: the app is a `wasi:http` guest
component (`wstd`, `wasm32-wasip2`), the patterns are a regexped component
(`wasm_format: component`), and `regexped merge` composes the two with `wac`.
`wasmtime serve` runs the result (`make run`), and so does FastEdge's own local
runner, `@gcoredev/fastedge-test`, which drives the FastEdge runtime
`fastedge-run` (`make test`).

It takes text as a POST body and answers a JSON array of the scripts its letters
use, each narrowed to the European alphabets its letters fit. Every pattern names a Unicode script class or a letter above U+007F, so
each compiles in Unicode mode, and a language is one anchored `match_all`
pattern over its alphabet:

```yaml
patterns:
  - name: German
    regexp: '(?:\P{Latin}|(?i:[a-zäöüß]))*(?i:[äöüß])(?:\P{Latin}|(?i:[a-zäöüß]))*'

sets:
  - name: latin
    match_all: latin_languages   # every language whose pattern matches the WHOLE text
    emit_name_map: true          # latin_pattern_name(id) names a language
    patterns: [German, French, …]
```

```rust
include!("stubs.rs");

let ids: Vec<i32> = scriptdetect::latin_languages(text)?.collect();
let names: Vec<&str> = ids.into_iter().map(scriptdetect::latin_pattern_name).collect();
```

The calls are the ones a module build makes; see
[component.md](component.md) for what changes under `wasm_format: component`.

## Go HTTP apps: componentize-go

`go build` cannot produce a component, but
[componentize-go](https://github.com/bytecodealliance/componentize-go) can: it
builds a stock-Go program (Go 1.27.1 or later) for `wasip1` and turns it into
one, generating the Go bindings for the app's WIT world as it goes. A regexped
component (`wasm_format: component`) plugs into that world through the `.wit`
regexped writes beside it, and regexped generates no Go code on this route:

```bash
# 1. Compile the patterns into a component and its sibling .wit
regexped compile --config=regexped.yaml               # → uaparser.wasm, uaparser.wit
cp uaparser.wit wit/deps/regexped-uaparser/

# 2. Generate the bindings for the app's world, which imports the
#    component's interfaces beside wasi:http/proxy@0.2.0
componentize-go -d wit -w ua-parser bindings && go mod tidy

# 3. Build the app, then compose it with the regexp component
componentize-go -d wit -w ua-parser build -o main.wasm
regexped merge --config=regexped.yaml --main=main.wasm uaparser.wasm   # → ua-parser.wasm
```

The app is a package `export_wasi_http_incoming_handler` with a `Handle`
function, which componentize-go's generated glue calls once per request, and it
calls the regexped component through the generated packages
(`regexped_<wit_package>_matcher`, `regexped_<wit_package>_sets`): a set's
`scan_all` is `Classify(input, 0)`, returning `witTypes.Result[[]uint32,
ErrorCode]`; a `groups_func` is a resource, `MakeEdgeVersion(input, 0)`, whose
`Next()` returns the next match's groups. [go-api.md](go-api.md#component-format-go-with-componentize-go)
has the whole mapping.

[`examples/fastedge/ua-parser/`](../examples/fastedge/ua-parser/) is a complete
app: it parses a User-Agent string — the request's own on `GET`, the body on
`POST` — into browser, OS, device type and bot, with one set `scan_all` over 23
patterns and a `groups_func` per pattern for the version. `make test` runs it
under FastEdge's own runtime, `fastedge-run`, through `@gcoredev/fastedge-test`.

**Local test runs are slow; FastEdge is not.** `fastedge-run` compiles the
module for every request, where FastEdge compiles it once when the app is
deployed, and a stock-Go component takes far longer to compile than a Rust one
— it carries the Go runtime. Measured on one machine (componentize-go 0.5.3, Go
1.27.3):

| App | Code | `wasmtime compile` | A request under `fastedge-run` | A request under `wasmtime serve` |
|---|---|---|---|---|
| Go (`ua-parser`) | 1.74 MB | 1.29 s | 1.16–1.31 s | 1.3–2.0 ms |
| Rust (`script-detect`) | 0.26 MB | 0.20 s | 0.21–0.23 s | 0.5–1.3 ms |

The last column is what a request costs once the module is compiled.

## JavaScript HTTP apps: the FastEdge JS SDK

The FastEdge JS SDK, `@gcoredev/fastedge-sdk-js` 2.7.0 or later, imports Wasm
components into a JavaScript HTTP app, and a regexped component
(`wasm_format: component`) is one. `fastedge-build` reads the interface from the
component, generates the JavaScript bindings and composes the component into the
app, so there is no stub to generate and no `regexped merge` step:

```bash
# 1. Compile the patterns into a component (and its sibling .wit)
regexped compile --config=regexped.yaml          # → secrets.wasm

# 2. Bundle the app, bind it to the component's interface, compose the two
npx fastedge-build --input src/index.js --output app.wasm \
  --component regexped:secrets/sets=secrets.wasm # → app.wasm
```

The interface is `regexped:<wit_package>/matcher` for single patterns and
`regexped:<wit_package>/sets` for sets; `wit_package` defaults to the
kebab-cased `import_module`. A config-driven build names it in the `components`
field of `.fastedge/build-config.js` instead of `--component`. The build also
writes `fastedge-components.d.ts` beside the input, with the interface's
TypeScript declarations:

| Config | JavaScript |
|---|---|
| `match_func: email_match` | `emailMatch(input): number \| undefined` — the end of the match |
| `find_func: email_find` | `new EmailFind(input, start)`, then `next(): [start, end] \| undefined` |
| `groups_func: kv_groups` | `new KvGroups(input, start)`, then `next()`: one `[start, end]` or `undefined` per group; empty when finished |
| a set's `find: find_secrets` | `new FindSecrets(input, start)`, then `next(): Array<{ id, start, end }>` — the matches at the next position; empty when finished |
| a set's `match_any` / `scan_any` | `f(input)` / `f(input, start)`, returning a matching pattern's id or `undefined` |
| a set's `match_all` / `scan_all` | `f(input)` / `f(input, start)`, returning a `Uint32Array` of every matching pattern's id |

Inputs are `Uint8Array`s and positions are byte offsets into them. An error —
the Backtracking engine out of memory, for example — is thrown as an `Error`
whose `message` and `payload` are the WIT error code (`'backtrack-overflow'`).

```js
import { FindSecrets } from 'regexped:secrets/sets';

const scanner = new FindSecrets(body, 0);   // body: Uint8Array
try {
  for (let ms = scanner.next(); ms.length > 0; ms = scanner.next()) {
    for (const { id, start, end } of ms) { /* id: the pattern's index in the set */ }
  }
} finally {
  scanner[Symbol.dispose]();
}
```

What SDK 2.7.0 requires of an app:

- **Dispose every scanner** in a `finally`. The bindings register a
  `FinalizationRegistry` to drop forgotten handles, but FastEdge's JavaScript
  engine never runs its callbacks, so an abandoned scanner holds its input until
  the request ends. A scan run to its end has already released its input and
  working memory, so only a scan that stops early holds anything. A `using`
  declaration does the same, but `fastedge-build` checks the syntax with the
  Node it runs on, and Node 22 rejects `using`; Node 24 accepts it.
- **Pass large data once.** Every call that passes data to a component leaves the
  bindings' copy of that data allocated until the request ends. Construct one
  scanner over the whole body and call `next()`, which passes nothing, rather
  than calling a component once per line or per word of a large body.

[`examples/fastedge/secret-redact/`](../examples/fastedge/secret-redact/) is a
complete app: it proxies an origin and masks AWS, GitHub, Slack, Stripe and
Google keys and JWTs in the text responses, with one set `find` over each body.
`make test` runs it under FastEdge's own runtime, `fastedge-run`, through
`@gcoredev/fastedge-test`.
