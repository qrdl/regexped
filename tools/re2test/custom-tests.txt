# Category 27 (FUZZER_BUGS.md #26): \b inside a capturing group loses the
# match entirely. Two distinct, unrelated root causes, both keyed on
# whether the two \b contexts (prev=word vs prev=non-word) require a
# DIFFERENT first byte — e.g. `\b[-0]` wants '0' after a non-word byte but
# '-' after a word byte:
#  1. compile/engine_dfa.go's find-mode fast-skip: computePrefix derived a
#     single "mandatory" literal byte from midStartState alone (ignoring
#     midStartWordState's possibly-different requirement), and the
#     firstByteFlags/Teddy fallback only ever looked at midStartState's/
#     startState's live bytes, never midStartWordState's — so the fast-skip
#     scanned for only ONE of the two valid candidate bytes, silently
#     skipping every match reached via the other context. repro:
#     pat="(\b[-0])" input="1-" — groups_func (composed behind this find)
#     wrongly reports no match. Exercises the DFA fix only: this pattern's
#     sole capture spans the whole match (task 41's trivial shortcut), so
#     no Backtracking captureBody re-walk happens at all.
#  2. compile/engine_backtrack.go's captureBody, independently: its
#     btWordBoundary treats pos==0/pos==len as the true start/end of the
#     input, but when composed behind a find wrapper those are just the
#     edges of the DFA-narrowed match slice — losing real \b context on
#     the other side whenever the narrowed slice doesn't start/end at the
#     original input's true edges. repro: pat="(\b[-0])x" input="1-x" —
#     confirmed still failing with only the #1 fix applied (outer find
#     correctly locates the match; captureBody's own re-check of \b at the
#     match's own start then wrongly fails it). "(-\b)"/"a-1" pattern below
